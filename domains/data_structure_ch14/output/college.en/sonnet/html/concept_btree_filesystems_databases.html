Btree Filesystems Databases

Definition

A B-tree of order $m$ is a balanced search tree in which every node holds up to $m-1$ sorted keys and up to $m$ children. Every non-root node is at least half full, and all leaves sit at the same depth. B-trees were designed for storage that is read in blocks (4 KB pages, say) and is slow to access. The goal is to minimize the number of block reads, not the number of comparisons.

If a node fits in one block, a lookup costs one disk read per level. With $N$ keys and minimum fan-out $t=\lceil m/2\rceil$, the height satisfies

$$h \le \log_t\!\left(\frac{N+1}{2}\right) = O(\log_t N).$$

Because $t$ is in the hundreds, $h$ stays tiny even for billions of keys.

Most real systems use the B+ tree variant. Interior nodes store only routing keys, which maximizes fan-out. All records live in the leaves, and the leaves are linked in a list, so range scans are sequential.

Worked example

Take a 4 KB page, an 8-byte key, and an 8-byte child pointer. Each key–pointer pair takes 16 bytes, so fan-out is about $4096/16 = 256$. If pages are about 70% full, the effective fan-out is $t \approx 180$. How many levels does an index over $N = 10^9$ rows need?

$$h \approx \log_{180}(10^9) = \frac{9}{\log_{10} 180} = \frac{9}{2.255} \approx 4.0$$

So about 4 page reads find any row among a billion. The top two levels (about 32,000 pages, roughly 130 MB) usually stay cached in RAM. In practice, one lookup then costs only 1–2 actual disk reads.

Problem-solving application

Where B-trees appear.

  • File systems: NTFS stores directory entries and file-allocation metadata in B+ trees. HFS+ and APFS keep their catalog (file and folder records) in a B-tree. Ext4 uses an HTree, a shallow B-tree-like index, for large directories, and extent trees to map file offsets to disk blocks.
  • Databases: PostgreSQL, MySQL/InnoDB, and SQLite use B+ trees for primary and secondary indexes. WHERE id BETWEEN 100 AND 200 becomes one descent followed by a leaf-list scan.
  • Cloud key-value stores: Some use B-trees directly, such as LMDB and Amazon DynamoDB's storage nodes. Others, like Cassandra and RocksDB, use LSM-trees. The comparison is a classic design trade-off: B-trees give predictable reads, while LSM-trees favor write-heavy loads.

    • Problem. A table has $10^8$ rows with a B+ tree index of fan-out 100. A query selects 5,000 consecutive keys, and each leaf holds 100 records. Estimate the page reads.

    Solution. Height: $\log_{100}(10^8) = 4$ reads to reach the first leaf. The range spans $5000/100 = 50$ leaves. The first is already read, so 49 more sequential reads follow through the leaf links. Total: about $4 + 49 = 53$ reads. A hash index cannot answer a range query at all, and scanning the table would need about $10^6$ pages.

    Insertion keeps the tree balanced. If a leaf overflows, it splits in two and pushes its median key to the parent. A split cascades upward only when the parent is also full. Deletes merge or borrow from underfull siblings. Because the tree grows or shrinks only at the root, all leaves stay at equal depth, which gives guaranteed $O(\log_t N)$ cost for search, insert, and delete.
