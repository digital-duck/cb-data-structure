Payoff

Throughout this text, we have built upward from elementary sorting and recursion, through balanced binary search trees, toward a structure that must operate not merely in memory but against the brutal latency of persistent storage. The B-tree is the natural endpoint of that ascent. Every design decision we have encountered — minimizing height, maximizing branching factor, keeping nodes block-aligned — converges here, because the B-tree is the data structure that takes the geometry of storage hardware as its primary constraint rather than an afterthought.

What B-trees achieve. A B-tree of order $t$ guarantees that every internal node holds between $t-1$ and $2t-1$ keys and between $t$ and $2t$ children. The height of a tree storing $n$ keys satisfies

$$h \leq \log_t \frac{n+1}{2},$$

so with $t = 512$ (a value tuned to a 4 KB disk block) a tree of one billion records requires at most four disk reads to locate any key. Contrast this with a binary search tree, whose height can reach $\lceil \log_2 n \rceil \approx 30$ for the same dataset — thirty potential I/O stalls versus four. The reduction is not cosmetic; at a disk latency of 5 ms per seek, the difference between 150 ms and 20 ms is the difference between a responsive system and a frustrated user.

Worked example. Suppose a filesystem inode table indexes $n = 10^9$ file records, with block size $B = 4096$ bytes and each key-pointer pair occupying 16 bytes. The branching factor is $t = \lfloor B / 16 \rfloor = 256$. Then

$$h \leq \log_{256} 10^9 = \frac{9 \log 10}{\log 256} \approx \frac{9 \times 3.322}{8} \approx 3.74,$$

so $h = 4$. At most four block reads suffice to resolve any file path lookup, regardless of how many files the disk contains.

Key theorem (B-tree search complexity). Search, insertion, and deletion in a B-tree of $n$ keys each run in $O(\log_t n)$ disk I/Os and $O(t \log_t n)$ CPU operations. Because $t$ grows with block size while $\log_t n$ shrinks, B-trees remain efficient as storage capacities increase — a property no memory-resident tree can claim.

Lab cell.

import sympy as sp

t, n = sp.symbols('t n', positive=True)
height_bound = sp.log(n, t)
print("Height bound  :", sp.simplify(height_bound))

# Concrete evaluation: t=256, n=10^9
print("h ≤", float(height_bound.subs([(t, 256), (n, 1e9)])))

The B-tree does not merely solve the indexing problem — it reframes what "efficient" means once memory hierarchy enters the picture. Every major filesystem (ext4, APFS, NTFS) and every relational database engine (InnoDB, PostgreSQL) rests on this foundation. To see how these guarantees translate into the query planner that decides the cost of your SQL SELECT, choose one engine, open its source, and trace the path from a WHERE clause to a leaf node read. The mathematics you have just proved will be waiting for you at every turn.
