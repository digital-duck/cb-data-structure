Concept Book: Hash Collision Dos

Data Structure Ch05 · Generated by SPL

Payoff

Hash-collision denial of service (DoS) is the natural endpoint of this book because it uses every idea you have studied, and it does so in an adversarial setting.

What it achieves. A hash table promises $O(1)$ expected time per operation. That promise rests on an assumption: keys spread roughly uniformly over $m$ buckets. If an attacker can choose keys that all hash to the same bucket, each insertion must scan the chain built so far. Inserting $n$ such keys costs

$$\sum_{i=1}^{n} i = \frac{n(n+1)}{2} = \Theta(n^2),$$

instead of the expected $\Theta(n)$. A request body of a few hundred kilobytes can then hold a server's CPU for seconds. The attacker sends little data, and the server does a lot of work. This is an algorithmic complexity attack. It also shows the gap between average-case and worst-case analysis. Average-case bounds describe typical inputs. Worst-case bounds describe what an adversary can force.

Worked example. Suppose a server uses the weak hash $h(k) = (\text{sum of character codes}) \bmod m$. The strings "AB" and "BA" have the same character sum, so they collide. So do any two strings that are permutations of each other. An attacker can generate $n = 10^5$ distinct permutations of one string. The chain work is about $\frac{n^2}{2} = 5\times10^9$ comparisons, compared with $10^5$ for a healthy table. That is a factor of $n/2 = 50{,}000$.

Problem-solving application. The defenses follow from the analysis:

  • Keyed hashing. Use $h_s(k)$ with a secret random seed $s$ (SipHash is a common choice). The attacker cannot predict collisions, so the expected chain length is $O(1 + n/m)$ again, even against adaptive inputs.
  • Universal families. Pick $h$ at random from a family where $\Pr[h(x)=h(y)] \le 1/m$ for all $x \ne y$. This gives the expected-time guarantee without assuming anything about the input.
  • Structural fallback. Convert long chains to balanced trees, which bounds the worst case at $O(\log n)$ per operation.
  • Input limits. Cap the number of parameters or keys per request.

    • Application domains. Because no application domains were listed for this concept, the connections below are the ones the analysis points to:

  • Web servers and frameworks: parsing form fields, JSON objects, and headers into dictionaries.
  • Security engineering: treating complexity as an attack surface, alongside rate limiting and resource quotas.
  • Language runtimes: randomized hashing in Python, Java, and Rust.
  • Databases and caches: hash joins and in-memory indexes.

    • Invitation. Choose one domain and try it. Build a table with a weak hash, write a generator that produces colliding keys, and plot insertion time against $n$. Then swap in a keyed hash and watch the quadratic curve flatten. A web framework's request parser makes a good first target.
