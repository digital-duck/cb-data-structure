Concept Book: Treap Hashing Priorities

What the technique achieves

A treap stores each key $k$ with a priority $p(k)$. It is a binary search tree on keys and a heap on priorities. If the priorities are independent and uniformly random, the shape of the tree matches that of a random binary search tree. The expected depth of any node is then $O(\log n)$, and insert, delete, split, and merge each take expected $O(\log n)$ time.

Hashing priorities replaces stored random numbers with a deterministic function, $p(k) = h(k)$, where $h$ is a good hash function. This has three consequences:

  • No extra storage. The priority is recomputed from the key.
  • History independence. The tree shape depends only on the set of keys, not on the order of insertions and deletions. Two sets with equal contents always produce the identical tree.
  • Canonical structure. Equal sets give equal trees. Comparing sets, or detecting differences between them, reduces to comparing hashes of subtrees.

    • Worked example

    Take keys $\{3, 7, 9\}$ with $h(3)=41$, $h(7)=88$, $h(9)=17$, where a larger value means higher priority. Key 7 has the top priority, so it is the root. Key 3 goes left and key 9 goes right. Insert the keys in any of the $3! = 6$ orders and you get this same tree. A treap with stored random priorities would only give you this guarantee in distribution.

    Why it is the natural endpoint

    Earlier ideas fit together here. Randomized balancing gives the $O(\log n)$ depth bound. Hashing makes that randomness reproducible. Split and merge make the structure composable. Hashing priorities combines all three into one structure.

    Likely applications

    If you supply the intended domains, I can tie each one to the technique. Typical candidates include:

  • Synchronizing replicated sets, where canonical shape makes matching subtrees identifiable by hash.
  • Persistent and versioned data, where history independence lets identical subtrees be shared.
  • Verifiable or authenticated storage, where a deterministic shape gives every party the same Merkle root for the same data.

    • Invitation

    Pick one of these and build it. Try a small set-reconciliation routine. Hash each subtree, compare roots, and descend only where hashes differ. Then count how many nodes you visit when two sets of size $n$ differ in $d$ elements. You should find the cost scales with $d\log n$ rather than $n$.
