Payoff

What indexing achieves. Every comparison sort must distinguish among $n!$ possible orderings, so it needs $\Omega(n\log n)$ comparisons. Integer sorting via indexing sidesteps this bound by changing the question. It doesn't ask "is $a $$\text{pos}(v)=\sum_{uwhere $c_u$ is the count of key $u$. The total cost is $\Theta(n+k)$. When $k=O(n)$, that is linear time, which beats the comparison bound without contradicting it. The bound only covers algorithms that learn about the data through comparisons. Indexing reads the data's structure directly.

Why it is the natural endpoint. The earlier ideas in this book were arrays, constant-time access, counting, cumulative sums, and stability. Indexing sort uses all of them at once. It also shows a recurring lesson: a cost bound depends on the model of computation. When you know more about your inputs, you can often do better than a general-purpose method.

Worked check. Sort $[3,1,3,0]$ with $k=4$. The counts are $c=[1,1,0,2]$. The prefix sums give starting positions $[0,1,2,2]$. Scanning left to right, 3 goes to slot 2, 1 to slot 1, the next 3 to slot 3, and 0 to slot 0. The output is $[0,1,3,3]$. The two 3s kept their original order, so the sort is stable.

Connections to applications. The prompt lists no specific application domains, so these are the settings where the idea most often appears.

  • Radix sort. Stable counting sort on one digit at a time sorts $d$-digit keys in base $b$ in $\Theta(d(n+b))$ time. Fixed-width integers, IP addresses, and dates all fit this pattern.
  • Data processing. Histograms, frequency tables, and grouping records by small integer codes (ages, grades, categories) are indexing in disguise.
  • Text and genomics. Suffix array construction sorts by character codes, and DNA's four-letter alphabet makes $k$ tiny.
  • Graphics and imaging. Pixel intensities lie in $[0,255]$, so histogram equalization and median filters use the same counting trick.

    • Problem-solving habit. Before choosing a sort, ask two questions. Are the keys integers? Is the range $k$ comparable to $n$? If both answers are yes, try indexing first. If $k\gg n$, such as $k=n^2$, switch to radix sort with a base near $n$. That sorts in $O(n)$ time for any polynomially bounded range.

    Invitation. Choose one application and build it. Radix sort is a good first choice. Implement a stable counting sort, apply it to three-digit numbers from the least significant digit upward, and then work out why stability is what makes the later passes correct. After that, try the histogram-equalization pipeline and see how far the same idea goes.
