Payoff

The B-tree is the natural endpoint of this book because it resolves one physical fact: reading from disk is slow, and it happens in large blocks. A structure that is optimal for in-memory comparisons, such as a binary search tree, wastes most of every block it reads. The B-tree is built around the block.

What it achieves. A B-tree of minimum degree $t$ stores between $t-1$ and $2t-1$ keys per node, and every leaf sits at the same depth. Each node is sized to fill one disk block. For $n$ keys, the height $h$ satisfies

$$h \le \log_t\!\left(\frac{n+1}{2}\right).$$

Suppose a block holds about 255 keys, so $t \approx 128$. A tree of $10^9$ keys then has height at most

$$h \le \log_{128}\!\left(5\times 10^{8}\right) \approx 4.1,$$

so it is at most 4 levels deep. Search, insertion, and deletion each cost $O(\log_t n)$ block reads. Node splits and merges keep the tree balanced without any global rebuild. A binary tree over the same keys would need about 30 comparisons, and each one could mean a separate disk read.

Why it is the endpoint. Earlier chapters gave you the pieces: balanced search trees, amortized analysis, and the memory hierarchy. The B-tree combines them. It keeps the invariant that makes balanced trees fast and adjusts the node size to match the hardware. That makes it a model of how to design an algorithm for the machine that runs it.

Connections to applications. No application domains were listed for this concept, so the three below are the standard places B-trees appear. Check each against your own systems.

  • Filesystems. Directory indexes in NTFS, ext4 (HTree), APFS, and Btrfs use B-tree variants. Finding one file among millions takes only a few block reads, and the filesystem can grow without being rebuilt.
  • Relational databases. The default index in PostgreSQL, MySQL/InnoDB, and SQLite is a B$^+$-tree. All records live in the leaves, and the leaves are linked in order. A query like WHERE age BETWEEN 30 AND 40 therefore costs one $O(\log_t n)$ descent plus a sequential scan of the matching leaves.
  • Storage engines and caches. Keeping the top levels of the tree in memory means a lookup usually costs only one or two disk reads.

    • Practice check. For a table of $2\times10^{8}$ rows and a block that holds 100 keys, estimate the index height. Then say how many block reads a range query returning 5,000 rows needs.

    Invitation. Choose one application and study it in depth. A good option is to build a small B$^+$-tree index in Python, insert a million keys, and measure how block reads grow. Compare your measurements with the $\log_t n$ bound. Seeing the prediction match the data shows what this concept offers: a design you can analyze and then check against measurements.
